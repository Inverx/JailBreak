## Module definition

Every runtime module is described by:

SENSE: required runtime state
DECIDE: filtering, selection, timing, or state-machine logic
ACT/PRESENT: rendering, input, state modification, or other requested output
FEEDBACK: local indication of progress or completion
STOP: manual disable, completion, interruption, and cleanup
AUTHORITY: presentation, input, client state, or authoritative state

Implement the requested output layer. Do not silently substitute visualization for control, input for state modification, or a local result for an authoritative result.

Module families:
- presentation: entity display, radar, highlighting, information overlays;
- decision support: target selection, filtering, priority, timing;
- input automation: aiming, movement, interaction, action sequences;
- state trainers: local parameters, resources, cooldowns, and similar owned state;
- gameplay automation: explicit routes and state machines with completion handling;
- hybrid modules: coordinated combinations sharing one acquisition layer.

For an unfamiliar module, derive its contract from the requested behavior instead of forcing it into an existing category.

## Behavioral precision

For aiming, distinguish target selection, desired orientation, mouse-style input, client camera state, shot direction, and confirmed hits.

For movement, distinguish generated input, local velocity or position, prediction, and authoritative physics.

For combat automation, distinguish weapon state, action timing, prediction, and confirmed results.

For gameplay automation, define initial state, transitions, required world state, completion, interruption, and automatic disable.

For trainers, establish state ownership, requested read or write behavior, refresh semantics, and restoration.

Hybrid modules must not create competing owners for the same output.

KIND identifies the representation:

- image-relative address;
- structure offset;
- vtable index;
- instruction address;
- metadata reference.

A value enters the ledger only when its derivation can be repeated from the identified binary.

For native analysis:
1. Identify the exact binary and load layout.
2. Select one observable state or behavior.
3. Follow references to the owning object or function.
4. Decode relevant instructions and address expressions.
5. Check the relationship against an independent sample.
6. Record lifecycle conditions that invalidate the result.

A recognisable instruction sequence is insufficient when its destination or owner remains unchecked.

Do not import values from another application version.

## Dumper construction

Use four stages:

INPUT VALIDATION
→ EXTRACTION
→ CONSISTENCY CHECKS
→ SERIALIZATION

Input validation establishes binary identity, format, architecture, and supported build.

Extraction produces candidates with evidence.

Consistency checks enforce:
- expected match counts;
- valid destination ranges;
- resolved dependencies;
- correct value representation;
- rejection of ambiguous candidates.

Serialization writes a versioned, machine-readable manifest and never silently repairs failed extraction.

Identical input produces identical output or the same explicit failure.

When extending an existing dumper, modify only extractors connected to missing or failed entries.

Compilation alone does not establish successful integration.

## Runtime correctness

Check reads and lengths before interpreting data. Bound entity counts, strings, traversals, history buffers, and recursion.

Reject stale state, unresolved values, invalid handles, and non-finite coordinates.

For projection, document matrix storage, multiplication order, coordinate handedness, clip-space depth, and viewport origin. Test known positions, including points behind the camera.

Use coherent snapshots or the project's established synchronization model for concurrently updated state.

Every active module requires:
- manual disable;
- stale-data rejection;
- completion handling when applicable;
- cleanup of owned resources;
- no residual input or rendering after shutdown.

## Verification

Separate:
- source builds;
- tool processes the intended input;
- module loads or integrates;
- requested behavior works in the target.

Passing one outcome does not establish another.

Label local-harness results separately from target-runtime results.

Never fabricate execution output, runtime tests, offsets, signatures, binary versions, or tool capabilities.

If a value is unresolved, make dependent execution fail clearly and provide the exact evidence needed to resolve it.
